# ChrysaLisp 7.1

A shader language of our own, written as s-expressions, and the GPU to run
it on. The GUI moves to SDL3, a Raspberry Pi runs the desktop with nothing
under it, and a session keeps itself to itself.

**Update with `make install`.** The host programs and the boot image must
match, the table of calls between them has grown and the event the GUI is
given has changed, and an install from before this cannot build its way
forward. `make install` starts from the new `snapshot.zip` and builds the
host programs.

**The GUI is on SDL3.** `make install` uses SDL3 if it is on the machine, and
SDL2 if it is not, and says which. On a Mac, `brew install sdl3`. On Windows,
`install.bat` fetches `SDL3.dll`. `docs/intro/sdl3.md` walks through the
move, for an older Mac or a Raspberry Pi too.

**The launch scripts have changed.** A launch no longer stops every node on
the machine first, and `-b` is gone. `./stop.sh` still stops them all.

## The shader language

*	A shader is written as s-expressions, in a small typed language of its
	own, `lib/gpu/`. `definput`, `defconst`, `defglobal` and `defun`, floats,
	ints, bools and vectors, swizzles, `if`, `for` with a known limit, and the
	maths a shader needs. It is read and type checked in Lisp, and a back end
	is given the checked tree.

*	The value of a function is its last form, as in Lisp, and through the arms
	of a last `if`. `return` is for leaving early.

	```lisp
	(defun bigger :float ((a :float) (b :float))
		(if (> a b) a b))
	```

*	Five back ends. GLSL text, for OpenGL and WebGL. Metal Shading Language
	text. A SPIR-V module for Vulkan, the binary made word by word in Lisp, no
	outside compiler is called on. VP native code, for a machine with no GPU.
	And a Lisp lambda, which is the reference the others are checked against.

*	The native code back end turns a shader into a VP function, assembled once
	for the CPU of the node. It is 37 times as fast as the Lisp back end on
	the Macs and 84 times on a Raspberry Pi 4. The raymarch shader at 320 by
	240 takes 219ms on one core of an Apple M4, 377ms on a 2018 x86_64
	MacBook Pro, and 913ms on the Pi. It was run on ARM64, on x86_64, on the
	VP64 emulator, and on RISC-V 64 and LoongArch 64 under QEMU.

*	The inputs of a shader, the values of an app's controls, travel as one
	block of bytes, laid out as a GPU uniform block is, `(shader-pack)`.

*	New `shader` command. `shader file` shows what a shader is compiled to,
	`-t msl`, `-t spirv`, `-t vp`, `-t cpu` and `-t tree` for the other back
	ends and the checked tree, and `-o` writes it to a file. So a shader
	written here can be handed to a GLSL, a Metal or a Vulkan program that
	has nothing to do with ChrysaLisp.

*	`lib/gpu/shaders/raymarch.shader` is the surface raymarch demo,
	https://vygr.github.io/JS-Raymarch, ported. The back ends agree on it, on
	the M4's GPU through OpenGL and through Metal, on a Raspberry Pi 4's GPU
	through Vulkan, and on the two CPU back ends.

*	Every pixel the test suite checks, 42 of them over all its small shaders,
	comes out the same, to within 0.00005, from the M4's GPU through Metal,
	from the Pi's GPU through Vulkan, and from the CPU back end.

*	New doc, `docs/ai_digest/shader_language.md`.

## Shaders on the GPU

*	Graphics belongs to the GUI. A GUI app runs on the node that has the GUI,
	and a shader is drawn there, by the host GUI driver, into the texture of a
	canvas. There is no service and no message.

	```lisp
	(defq shader (shader-gui program))
	(. canvas :shade shader (shader-pack program vals))
	```

*	The driver builds a shader on a thread of its own, the GUI does not stop
	for it. `:shade` returns `:nil` till it is built, and `:error` if it can
	not be.

*	A shader can be drawn into part of a canvas, `(. canvas :shade shader
	block x y x1 y1)`, and one draw is on the go at a time, so a GPU that
	takes long over a frame can be given it a strip at a time and the desktop
	is drawn in between. `(. canvas :exchange that)` swaps the textures of
	two canvases, to show a frame only when it is whole.

*	`(. canvas :swap +swap_read)` reads the texture of a canvas back into its
	pixmap, which is how an app gets at the pixels the GPU drew.
	`+swap_write` is the pixmap to the texture, the way a swap always went.

*	The surface demo, `apps/demos/surface`, in the launcher under Demos. It
	makes a slider for each input of the shader, comes up on the GPU, and has
	a CPU button, which farms the frame over the nodes as native code. A 640
	by 480 frame on an Apple M4 Max is drawn by the GPU at the 60 a second of
	the demo's timer, and takes 76 to 96ms on 16 nodes with none.

## The host

*	A new GUI driver on SDL3, `src/host/gui_sdl3.cpp`, with SDL's GPU renderer
	for the 2D drawing and SDL's GPU interface for the shaders, on the same
	device. Metal on a Mac, Vulkan on Linux and Windows. It is the default.

*	The GUI drivers are `sdl3`, `sdl`, which is SDL2, `raw3` and `raw`, which
	do their own drawing and use SDL for the window alone, and `fb`, the Linux
	frame buffer. `make GUI=sdl` asks for one by name. The SDL2, raw and
	frame buffer drivers can not draw a shader, and say so.

*	The sdl3 driver needs SDL 3.4 for the shaders. On an older SDL3, the 3.2
	of Debian 13, it builds without them and the GUI is the same.

*	A GUI driver gives the GUI an event of our own, `src/host/gui_event.h`,
	not a copy of an SDL2 event, and the fake SDL header the frame buffer
	driver needed is gone.

*	A blit in a color tints a glyph or a greyscale texture and no other, on
	every driver. The SDL drivers used to tint anything.

*	`docs/ai_digest/host_interface.md` has the shader calls, the clipboard
	calls, the five GUI drivers and the two audio drivers in it.

*	The frame buffer driver was run on a Raspberry Pi 4, the launch script,
	four nodes, the desktop, Onslaught and the surface demo. Four old faults
	in it are fixed. A mouse moving at a steady rate did not move the
	pointer. A tinted texture had its red and blue swapped. The console's
	text cursor flashed through the desktop. And the Escape key ended the
	node.

## Sound

*	The SDL3 audio driver does its own mixing, 32 voices, each with its pan,
	so there is no mixer library to install. A loud mix is limited, not
	clipped, eased in from 90% of full scale.

*	The mixer is a file of its own, `src/host/mixer.h`, with no SDL in it,
	for whatever audio driver comes next.

*	A node whose host has no audio driver, the TUI host, or a GUI built for
	the frame buffer, no longer crashes if the audio service starts on it.
	The login app starts the service on the GUI's own node.

*	It stays on a thread of the host. A ChrysaLisp task that asked to be
	woken every 5ms, on a node also shading tiles of the raymarch shader, was
	up to 44ms late on an M4 and 171ms late on a Raspberry Pi 4, and a sound
	device has to be fed on time.

## Sessions and desktops

*	A session, the nodes one launch script started and the nodes they started
	in turn, stops only itself. Two sessions on a machine do not meet, each
	has link names of its own, and closing one leaves the other alone.

*	A desktop is a node. `nodes -g 1` in a terminal adds a GUI desktop, to a
	TUI network as well, and `nodes -t 1` a node on the lighter TUI host.
	Quit closes a desktop and leaves the rest of the session up. A session
	lives while it has a way in, a terminal or a desktop, and stops when the
	last has gone.

*	Shutdown, on the logout panel beside Quit, stops every node of this
	machine at once.

*	The GUI leaves the apps on its node some time between frames. Where the
	display is slower than the GUI's timer, a 50Hz TV, a window being dragged
	did not move till the mouse stopped.

## Raspberry Pi

*	The GUI runs on a Raspberry Pi 4 with no desktop under it, Raspberry Pi OS
	Lite, SDL3 on the bare display, and the Pi's own GPU draws the shaders,
	through Vulkan and the SPIR-V back end. On Debian 13, with SDL 3.4.16
	built from source, which takes the Pi a little over three minutes.

*	The raymarch frame the Pi's GPU draws is within 0.0025 of the CPU back
	end's on every pixel. It takes that GPU about 400ms for 640 by 480. The
	surface demo draws it in strips, at 1.5 to 1.8 frames a second, and the
	desktop is drawn 50 times a second while it does.

*	The Pi's driver takes 18 seconds over that shader the first time it sees
	it, then keeps it. The demo draws on the CPU till it is built.

*	`make install` on the Pi, host programs and all, takes 40 seconds.

## Memory

*	A canvas can free its pixmap once it is a texture, `(. canvas :swap
	+swap_flag_free)`, `(. canvas :free)` and `(canvas-load file
	+load_flag_free)`. An image that is only ever shown no longer keeps its
	pixels in memory twice.

*	The images of Onslaught held 4.7MB, 18.4MB and 36.7MB at zoom 1, 2 and 3,
	and now hold 7KB, 27KB and 40KB. The wallpaper went from 7.0MB to 0.8MB,
	the image viewer from 6.4MB to 0.3MB, the PCB viewer from 2.3MB to 0.8MB.

## Not ready

*	The sdl3 driver has not been run on a Linux desktop, X11 or Wayland, only
	on Macs, on Windows, and on the bare display of a Raspberry Pi.

*	The frame buffer build has no sound, it has no audio driver. And the
	Pi's frame buffer is 16 bit, so gradients show bands.

*	A TV plugged into a Raspberry Pi that was already running lost the
	picture, on and off, the first time the GUI ran. It was steady when run
	again and after a reboot, and is not explained. Start the Pi with the
	screen attached.

*	Compute shaders, vertex shaders, meshes and textures as inputs are not
	here. A shader is a fragment shader over a canvas.

*	A network with 7.0 and 7.1 nodes in it has not been tried.

*	The `fmt` command is still parked. Do not use it on the tree.
