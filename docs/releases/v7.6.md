# ChrysaLisp 7.6

One build, checked. The release mode is gone: every build has its error
checks, and `catch` and `throw` behave the same wherever code runs. The
build is faster again, the VP binary encoder is VP, and every host lists
a folder in the same plain terms.

**Update every machine with `make install`, once.** The host programs
have changed, a folder's entries come back in new terms, and the build
needs the VP encoder that the new `snapshot.zip` carries. A tree from
before cannot build its way forward.

**Then start the rack member again, once**, `./rack.sh down` and
`./rack.sh up`, or `rack.ps1` on Windows. The host program has a new
name, and a member from before looks for the old one after its update.

## One build mode

*	There is no release mode. A build is normal, with its error checks,
	or `validate`, normal and more checks as it runs. `make` takes
	`validate` and nothing else for a mode. The VP of a build is kept in
	`obj/vp/`, a validate one's beside it in `obj/vp_validate/`, so a walk
	of `obj/vp/` sees the normal VP alone.

*	A `(validatecase)` must use no more registers than the code round it,
	so the trashes of a function are the same in both modes. `lint`
	checks it: `make trace validate` makes the VP of a validate build
	alone, no code of any platform, and `trace` runs over
	`obj/vp_validate/` as over `obj/vp/`.

*	The checks cost nothing that can be measured. `make test`, an MP3
	decode and an HE-AAC decode run the same with and without them; the
	emulator builds about 5% faster without, and the images are about 10%
	smaller. Not worth two builds that behave differently.

*	`catch` and `throw` work the same in every build. A throw in the
	middle of a function, or one used as a test, is caught as it should
	be; in a release build it went on as a value. They are there for
	faults, not for steering normal code.

*	The `errorcase` and `noterrorcase` forms of the VP assembler are gone,
	what was in an `errorcase` is plain code, and `errorif` is `gotoif`.
	`validatecase` is the one build-dependent form left. A normal build
	is the same to the byte as the debug build was.

## The build

*	`make test`, a full build, is back to 53 to 55 ms on an M4 from 66 to
	68: the VP binary encoder is VP, `lib/trans/vpb_encode.vp`, every
	function of the system encoded in 6 ms where the Lisp took 93.

*	The VP64 boot image carries the encoder as it carries the
	translators, so an install encodes with it; the Lisp encoder is gone.

*	A forced make, `make all`, translates the translators from their VP as
	any file, where it built them twice, one stage after the other: 28 to
	33 ms in place of 81 to 100.

*	One VP per build mode. A function's VP binary is only in its file's
	bundle in `obj/vp/`, and the loader finds it there,
	`(:sys_load :vp_find)`, when it binds a function that has no native
	code; no `.vpb` beside each native, some 6,400 files fewer.

*	The VP spec says what an operand may be: a register, a number, a
	label, a distance between labels, a string, a name. Not a fixed, a
	real, or a form left to be worked out; the encoder refuses anything
	else and the build stops with the function's name.

*	A fused `assign` in vpx whose source is also a destination stored
	before it reads it first; it read the new value.

*	The VP loads and stores a 32 bit float, as a GPU has its floats:
	`vp-cpy-if-i`, `vp-cpy-fi-i`, `vp-cpy-df-i` and `vp-cpy-fd-i`, the
	`-i` of the memory as an int's is. A float register is a double
	still: a single is made a double as it is loaded, and the nearest
	single to a register is stored, the register not changed. `assign`
	takes them, of a 32 bit place and a float register. Every
	translator and the VP64 emulator has them, so a buffer of singles
	is read and written natively, not a float at a time in Lisp.

*	The Benchmark app times what `make test` does.

*	The VP optimizer knows of floats when it looks back over memory. A
	float store now ends the search for what was stored there, and a load
	of the place, a float's or one of another width, keeps the store before
	it. Neither changes a function built on arm64 today. A store by a
	register index is still not seen.

## Hosts and files

*	There is one host program, `chrysalisp`, `chrysalisp.exe` on
	Windows, where there were `main_tui` and `main_gui`. Every node is
	it, a terminal's and a desktop's. A node has a GUI and audio if the
	host found them as it started, and a desktop is a node that runs the
	GUI service. `make` builds it, `make install` as before; the `gui`
	and `tui` targets are gone.

*	SDL3 is not linked, the host loads it as it starts,
	`src/host/sdl3_load.h`: the one it was built with, else the one the
	system finds by name, or only the one `CL_SDL3` names. With no SDL3
	it runs on, with no GUI and no audio, as the old terminal host did.
	Loading it costs a node 2 to 3 ms to start. With neither SDL3 nor
	SDL2 to build with, `make` builds it with no GUI, `GUI=none`, and it
	needs no library at all. SDL2 builds still link SDL2.

*	On Windows the host is a console program, so a terminal works as it
	is, and a desktop's console is hidden by the scripts that start it.
	The snapshot carries the one program.

*	`(pii-chmod)` on Windows now makes a file read only or not, where it
	did nothing: the only part of a mode a file has there.

*	Every node now has the host's film decoders, where its host has
	them, not only a desktop's node.

*	Compute on the GPU, `lib/gpu/compute.inc`, on any node of a host on
	SDL3, a desktop or not: buffers on the GPU written and read back, and
	kernels, MSL text on a Mac, a SPIR-V module elsewhere, run over them
	with a block of uniforms. It is a fifth table of the host,
	`src/host/gpu_sdl3.cpp`; its device is made the first time it is
	wanted, with no window, and the GUI driver draws with the same one.
	Work goes in order on the GPU's queue, a dispatch and a read give a
	ticket, and `(gpu-wait)` gives way to the node's other tasks till it
	is over. Run on the M4 and x64 Macs by Metal and on the Raspberry Pi 4
	by Vulkan.

*	The shader language has kernels. A file with buffers, `(defbuffer name
	:float|:int :read|:write)`, is one, and its `main`, `(defun main :void
	((i :int)) ...)`, is run once for each index of a range, reading and
	writing them with `elem-get` and `elem-set`. Ints have `logand`,
	`logior`, `logxor`, `<<` and `>>`. The MSL and SPIR-V back ends make it a
	kernel for the GPU, `(shader-gpu-kernel)` and `(shader-gpu-run)` in
	`lib/gpu/kernel.inc`, and the VP back end a native function that runs
	the range, `(shader-vp-kernel)`, so the one source runs on a GPU or on
	any CPU. The CPU, the VP and the GPU give the same bytes, on the M4 and
	x64 by Metal and on the Pi by Vulkan. An int literal of 32 bits written
	as its bits, `0xff000000`, is taken as them.

*	`lib/motion/`, a 2D scene graph of vector figures with the place of each
	in 3D, for presentations, games and lessons. A figure has attributes, and
	components that control any of them: `Tween` by an ease, `Rate`, `Wave`,
	`Follow`, `Tie`, `Cues`, `Custom`, a colour by its channels and an outline
	by a morph. Bounds, a sweep, then polygons, for routines fired when figures
	come to touch, go on touching and part, and when a component ends. See
	`docs/ai_digest/motion.md`. A window can keep the shape of a view of it as
	it is dragged, `:aspect_view` and `:aspect`.

*	A host call takes at most six args, the most the x86_64 translator
	moves, and the assembler now says so when one is given more.

*	Every host lists a folder's entries as `f` a file, `d` a folder or
	`l` a link to a file, not Unix's `d_type` digits. `.` and `..`, a link
	to a folder, and anything else are left out, so a walk of the tree
	cannot go round a link; a link, or an entry a file system does not
	type, is asked of the entry itself. Sync goes through no link.

*	A file stream's read or write of a buffer or more goes to the host as
	one call, past the buffer, not a buffer at a time. Its buffer stays
	the size it was. A store on an exFAT stick under macOS put its blocks
	four times faster for it: each call to the host there costs far more
	than the bytes do. A stream class says whether it can with
	`:read_direct` and `:write_direct`, and only the file stream does.

## Media

*	The SVG loader's skewX and skewY are skews: they were made with cos
	and sin, a part turn and not a lean, where a skew is 1 and tan of the
	angle. Its matrices are lib/math/matrix.inc's `mat3x2`, the six fixeds
	`mat3x2-vec2-mul` takes, where it had copies of its own; the skew is
	`(mat3x2-skew ax [ay])` there. Every SVG of the Images app draws the
	same to the byte, none of them skews.

*	A 3x2 matrix by a matrix is native, `(mat3x2-mul ma mb [out])`, on
	:path beside the matrix by each point of a path, which is now
	`:path :mat3x2_v2_mul` and `(mat3x2-vec2-mul m3x2 src dst)`, where it
	was `:transform` and `path-transform`: the names of the 4x4 real ones,
	`mat4x4-mul` and `mat4x4-vec4-mul`. `mat3x2-mul` uses it, about nine
	times faster, the same to the bit, each product shifted as a fixeds
	dot shifts it.

*	The matrix makers of lib/math/matrix.inc are lower case, `mat3x2`,
	`mat3x2-rot`, `mat4x4-rotx` and the rest: a capital is a class, and
	they make a fixeds or a reals. The matrix of no change is
	`+mat3x2_unity`, held once, in place of :nil: every 3x2 function takes
	a matrix and only a matrix, `mat3x2-mul` among them. An item of a
	whiteboard with no place has it, and every matrix is used as it is,
	with no test for no change: over the 256 documents of the tree drawn,
	such a test found it in 22 of 23,664 shapes. A drawing function's
	matrix is optional where it was a :nil, `cwb-draw-items` among them.

*	MP3 and SBR synthesis keep their filterbank's history as a ring: the
	new block is written in, nothing moved. MP3 decodes 12% faster.

*	SBR's high band is made a slot at a time by one native, into the slot
	in place. With the ring, HE-AAC decodes about 7% faster. The samples
	are the same to the bit.

*	SBR's energy estimate is one native over the slots of each band, its
	mapping refills only the envelopes there are, and its low band is
	gathered once. HE-AAC decodes about 10% faster again, the samples the
	same to the bit.

*	A reader of `lib/media/bits.inc` read past the end of its str, or
	before its start, as a corrupt stream can make it, reads 0s, not what
	is after the str: the str has 32 bytes of 0 after it and the natives
	read no further in than 16 before its end. MP3 and AAC stop there too.

*	Films on a Linux PC decode H.264 and Motion JPEG on its graphics, by
	VA-API, where the machine has a driver: Intel's, AMD's is untested.
	Every Linux host has it, no `libva-dev` to build it, what it uses of
	libva declared in `video.cpp`; libva is loaded as it is wanted, so the
	host still starts without it, and anything VA-API can not do goes to
	V4L2 as before, so a Raspberry Pi is as it was. See `docs/intro/intro.md`
	for the packages. A 1080p frame is about 14ms on an i5-7200U.

*	Films on a Linux PC decode H.265 on its graphics too, by VA-API, Main
	and Main 10, and Main Intra of the range extensions with none of their
	tools: an MKV or MP4 of 4K HDR as a UHD Blu-ray has it. A picture is
	made from the pictures its stream says it keeps, and one
	made from a picture not there, as after a seek, is not decoded. Every
	field the driver is given is the same as GStreamer's `vah265dec`
	gives it, of x265's clips and 4K of a film, and the pictures the same
	to the bit as `avdec_h265`'s. A picture of 4K is read and made pixels
	by up to 4 of the CPU's threads, and the memory of one shown kept for
	the next, so H.264 of 4K is faster too.

*	Films on a Raspberry Pi 4 decode H.265 on its own hardware, of 8 and
	10 bits, by V4L2's stateless decoder, `rpi-hevc-dec`, with what is
	parsed for VA-API. A picture comes back in columns and is made rows.
	A real film of 1080p, 53 frames a second of 8 bits made pixels, 30 of
	10 bits, 21 of HDR with its tone map. The same to the bit as a
	software decoder on 17 of 19 kinds of stream of 8 bits and all 6 of
	10. The other 2, 16x16 CTUs and lossless CUs, are the same as FFmpeg's
	use of this hardware: that is the hardware.

*	HDR, of PQ or HLG, is shown on an SDR display as it is meant to look:
	each of R G and B made light, BT.2390's tone map from the film's
	brightest, its MaxCLL or its mastering display's from the SEI, to the
	SDR white of 203 nits, BT.2020's primaries made BT.709's, and a PC
	display's gamma of 2.2. SDR of BT.2020 has its primaries made
	BT.709's. By tables, and AVX2 where the CPU has it, the same to the bit as the
	scalar: a 4K frame of HDR about 30ms in the power saver's 800MHz of
	an i5-7200U, with its decoding about 64ms in all, 15 frames a second,
	a third of that at its usual clock.

*	The pictures of VA-API are made pixels by the colours their stream
	says, BT.709, BT.601 or BT.2020, or by their size if it says none, HD
	709: before, all were BT.601, the colours of HD a little off.

*	AAC whose channel pairs have no common window, as FFmpeg's own coder
	makes, decodes: such a pair was taken through M/S, the right read by
	the left's bands, and Films stopped on it with `not_valid_index`
	(#340). M/S is only where it is sent, and intensity is by the right's
	own window.

## Code between systems

*	A system names its server zero by the waypoint it is at: `make
	install` notes the commit it built at, `obj/installed`, if the tree
	is exactly at its waypoint, and a `make` that builds after takes it
	away. A task sent between two systems at the same waypoint reads its
	files and binds its natives where it lands, and neither `@Source` is
	asked anything. `make install` notes the waypoint itself, as the
	`waypoint` command does, so a pull and an install is all it takes.

## Robustness

*	A desktop that quits takes with it the nodes it started, and those
	they started, unless a desktop or a terminal is still up among them:
	`nodes -a` in a terminal on a desktop the member started left its
	nodes running when the desktop went. `(node-leave)` follows the notes
	of what each node started, as a session's end does.

*	A soft edged fill of a wide shape is a third faster. `:canvas :fpoly`
	draws soft edges through a coverage mask it flushes to the row every
	eight scan lines, walking from each edge to the next a byte at a time:
	a wide span walked its whole width. The walk now goes eight bytes at a
	time while eight are in the row and all 0. A disc or a box of 400
	across, soft, 31 to 38% less; text, many small shapes, the same as
	it was; hard edges untouched, they take no mask. Each measured as the
	best of three fresh sessions against the old code's own spread, which
	for text is some percent between sessions.

*	The arm64 translator's unsigned byte and short loads are one
	instruction. `ldrb` and `ldrh` into a W register zero the rest of it,
	as `ldr w` does, and the translator put an `eor` of the destination
	before them, or a `ubfx` after when the destination was the base: an
	instruction wasted at each of 553 loads, in the string, stream and
	UTF-8 code. Found by fitting each function's native size to its VP ops.

*	Macro expansion of a wide form goes to its end. The expander walks a
	form with a stack of the lists still to be looked at, which a wide
	form fills as a deep one does, and at 1,000 of them it stopped going
	down, with nothing said but a debug line: a form of more than a
	thousand lists had macros in the first of them left as they were. The
	stack grows as it must now.

*	`(first :nil)`, `(second :nil)`, `(third :nil)` and `(last :nil)` are
	`:nil`, as they are of a list too short, and `(rest :nil)` and `(most
	:nil)` a new empty list. A symbol is its chars, so they were `:`, `n`,
	`i`, `l`, `nil` and `:ni`, and a test for `:nil` after them was never
	met. Asked for the native of a function
	it did not build, a kernel made as it ran, `@Source` so said it had
	one, a hash of `:` calling a function `n`, and the node asked tried to
	translate that and went down, with all on it.

*	`@Source` gives a shader as well as Lisp, so a child sent to another
	system can read the kernel it runs: Mandelbrot's children there died
	as they took their first square. They still run on the machine of the
	app, by its own choice.

*	A farm's child that can not do its work where it is can say so,
	`(. jobs :cannot msg)`: its job goes back on the queue, its node is
	left out, and a child is started on another. Only the fast path, with
	no word the farm's patience does the same for the job and the child.

*	A system's `@Source` can be more than one for a while, and any that
	is held can go: two started at once give way to the lowest, and a
	session's own can come up after one a task started. Whoever holds one
	finds it again when it says nothing. `(source-ask)` of this system's
	looks up the one there is now after each `+source_wait` of silence and,
	if that is another, asks it; one still there is busy and is not asked
	twice. One that gives way answers what still comes to it itself, and
	sends nothing on: the one that stays, asking it, waited on itself.
	test_source failed or hung when three machines were tested at once.

*	A recording played back by the Storage app, or a test, has its lines
	in the order of their times, not the order they came: they come in
	batches, and mail is not in order, so under load a batch could come
	before the one sent ahead of it, and the store was replayed wrong.

*	A number read from text ends at the first character that is not a
	digit of its base, or the point: `(str-as-num "5\n")` was 44, the
	newline read with it from a file taken as a digit, and a space after
	one did the same. The reader and an SVG path's numbers read the same.

*	A bundle of VP binary cut short, or one that says a length past its
	end, as one from another node may, gives what is whole and reads no
	further; the name of a binary that is not whole is "".

*	The storage tender takes a peer that did not answer, or said less
	than it was asked, as not having a block, where it stopped.

*	A storage service asked which of some blocks it has, by names that
	are not a whole number of 32 bytes, as a peer of another build may
	ask, answers for the whole names; it ended.

*	A storage service told to stop answers once its volume is closed and
	let go of, so the caller may remove the image then. It answered
	first, and Windows removes no file that is open.

*	A desktop told to quit while its apps were still starting never went: a
	window that came after the quit was never told. Each is now closed as
	it comes.

## Storage

*	A store opens about five times faster. Of 1.48 million blocks, 86 GB
	more than at #329, the open was some 12 minutes of an i5-7200U, now
	under two and a half. The names of the volume's entries were made a
	character at a time, and made again for the index of each folder:
	now a name of ASCII, as a block's is, is its low bytes split from
	its 0s, and its key is its own `to-upper`. Each entry is read where
	it is, not copied out first.

*	The open lists the folders of `blocks/` one after another, no walk
	of a tree, and the blocks of one share its path. Its map of what is
	held has a bucket for every four blocks, not 1021 for a million, and
	the store counts its blocks, so the service and `(store-info)` do not
	add up the buckets for it.

*	The manifest of a big object is a tree of blocks of no more than 1000
	names, none bigger than a block of the object (#332). It was one block
	of any size: of an 86 GB file 85 MB, sent whole as the commit, and had
	whole to read the file back, so a client's wait of 10 s ran out on
	both. Now a writer puts the blocks of the manifest as blocks and
	commits only the name of its top, and a reader has it a block at a
	time; a stream asks which blocks the service has 1000 names at a time.
	An object of 1000 blocks or fewer has the one block it always had, and
	a store of before is read as it was.

*	A stream of an object, and `(storage-read)`, have its manifest a part
	at a time, as it is read: the top when it is opened, and a block of
	1000 names, and which of them the service has, when a block it names
	is wanted, `(storage-pages)`. It had all the names, and asked of all
	of them, before the first byte: an 86 GB film took 27 s to open, 14 s
	with its manifest a tree, and now 2 ms. A seek has only the part of
	the manifest of where it lands. A manifest of one block of before is
	had 1000 names at a time the same.

*	A block put that has no answer is `:lost`, not `:full`: a store that
	was busy said it had no room.

*	A store is opened with a file of the blocks it keeps, `held`, written
	as it is closed, in place of reading every folder of `blocks/`: 20,000
	blocks open in 7 ms where the folders took 132 ms on the M4, and a
	million blocks that took minutes on an i5 should take seconds. The
	file goes as soon as a block is put or let go of, so a store not
	closed as it should be is read from its folders, as before, and the
	file written then.

*	The maps of a store, of its blocks, paths and plan, grow with it, a
	bucket for every 32 in them: they had a fixed number, a few thousand,
	whatever the store held.

*	A store's volume has clusters no bigger than its blocks. A block is a
	file and takes a cluster at least, and exFAT's own clusters of a volume
	over 32GB are 128KB: of a store of 64KB blocks, half of it was never
	used, and one of 96GB was full at 51GB of blocks. Stores made before
	keep the clusters they have.

*	`storage -s` waits for the store as long as its service is there: one
	made on a slow stick is minutes writing, and the fixed wait said none
	was made of one that was, and did not make the machine its member.

*	`storage -w` and `storage -c` wait as long as the service is there,
	`(storage-ask)` with a wait of `:t`: a sweep or a check of a store of
	a million blocks is minutes, and the waits of 60 and 120 s gave up
	while it went on, a sweep said `:nil blocks let go of.` (#341).

*	A machine that is a member of a store on a stick that is not there,
	not mounted, starts no store and says nothing, and starts it once it
	is: the claim of the image threw as its note could not be written,
	and the store's starting at boot ended there.

*	`storage -l`, `-k` and `-M` say when the store did not answer in
	time, a store busy for more than 10 s. `-l` walked the `:nil` of no
	answer as its letters and failed with `wrong_num_of_args`, and the
	column of how many members have an object said `0/0`, now `?` (#341).

*	`(storage-copy-object)` copies an object from one store to another,
	of this machine or of another, of one mesh or not, through no file:
	only the blocks the store it goes to has not got are had and put, a
	few at once, and its dial of copies goes with it (#333). A store of
	blocks of another size has it read as a stream and put.
	`(storage-get-file)` writes an object out to a file of the host, a
	file there already written over only once all of it has been had, and
	`(storage-put-stream)` puts the blocks a service has not got a few at
	once. Each takes a tick, told of the bytes as they go, that can stop
	it, the path then as it was.

*	`storage -c -v` checks the volume a store is on, `(exfat-check)`:
	every file and folder as the disk has it, from the root, with a cluster
	two of them have and who has it, one in use the bitmap says is free, a
	chain that ends before its length, a folder held in memory that is not
	as the disk has it, and how many clusters are marked in use that
	nothing has. It reads folders, not blocks, and only reads (#341).
	`storage -C -v` mends it as well, `(exfat-check vol :t)`: a cluster in
	use is marked in use, one nothing has is let go of, a folder held that
	is not as the disk has it is read again, and a last line says how
	many. A cluster two have, a chain cut short, are only said.

*	A rack member is asked to stop, not killed: `rack.sh down`, and a
	commit followed, leave `/tmp/chrysalisp_rack_stop`, and the member
	closes the stores kept on its node, `(storage-stop-here)`, before it
	ends, as it now does too when it ends to be updated. Only one that has
	not ended in 60 seconds, `CHRYSALISP_STOP_WAIT`, is killed. Both
	`rack.sh` and `rack.ps1`.

*	An exFAT volume whose task is killed part way through a write, as a
	member stopped for an update is, is left with room lost at worst,
	never a cluster a file or folder has that the bitmap says is free,
	which the next file was given and so spoilt. A long write writes out
	its full cache as it goes, folders and table with it, and the bitmap
	was written only at the end. Now each write out puts the bitmap first,
	with the clusters given out in use and those let go still in use,
	then the rest, then the bitmap as it is; and a cluster let go is not
	given out again till that last is written (#341).

*	exFAT finds free clusters by `(fs-bit-run)`, a native of
	`lib/fs/lisp.vp`: the first run of so many clear bits of the bitmap, a
	byte at a time where a byte is all used or all free. Over a million
	clusters, a full bitmap is 60 us where it was 22 ms, and one with a free
	cluster every 64th 157 us where it was 102 ms, every one of them read a
	bit at a time. A file's chain is followed a block of the table at a time,
	4,000 clusters in 658 us where they were 3 ms, a cache lookup each.

## Apps

*	Mandelbrot flies. The left button held flies in, the right flies out,
	about the point under the pointer, which stays under it; where the
	pointer is from the middle pans that way, buttons or not, and at the
	middle it holds still. Nothing steps, each frame moves on by how long
	the last took, the speeds ease in and out, and the zoom and the pan
	slow to a stop at their ends. The picture is one kernel of the shader
	language, `kernel.shader`, in place of a kernel written twice by hand
	and the VP shade. On the GPU a frame is the whole picture, a pixel a
	thread; there it goes as deep as a float of 32 bits can tell one pixel
	from the next, 20000 times. With no GPU the children of the farm run the
	same kernel as native code, in reals, each a square a ring at a time
	from its edge in, and all on the nodes of the app's machine. CPU and GPU
	buttons switch between the two, and the time a whole picture takes is
	shown, to compare them. A new picture does not start the children
	again, its answers come to a new mailbox and those of the last are let
	go. Each pixel is four points of the set, and the middle of
	the picture is on the grid of its pixels, so it does not shimmer as it
	moves. Seven palettes, chips on the toolbar: the gold, blue and white
	there has always been, fire, ice, ink, sunset, forest and spectrum.

*	Motion, `apps/demos/motion/`, tells where this system came from, Games to
	VP to Taos to ChrysaLisp, in about two minutes of vector figures, and has a
	playground of balls that meet and burst. Nothing in it says what happens
	when: the end of a caption, the last bar to reach the middle or the last
	tile of a picture brings on what is next. Play, pause and restart. Its window
	keeps the shape of a 640 by 480 picture as it is dragged, and the picture
	is drawn to fill it.

*	Spectrum, `apps/games/spectrum/`, a ZX Spectrum 48K, with six of the
	games of Mikro-Gen it plays: Automania, Pyjamarama, Everyone's A Wally,
	Frost Byte, Battle Of The Planets and Laserwarp. The Z80 is VP: a native
	call runs a frame, 69888 T states, with the Z80's registers held in VP
	registers all through it, and its state read and written only as it
	starts and stops. A handler for each opcode is made by Lisp as it is
	assembled, an index prefix puts IX or IY where HL is, and it is 20 KB on
	ARM64. It passes all of zexall, and runs it at some 1300 times the speed
	of a Spectrum. A tape is loaded at once by a trap at the ROM's LD-BYTES,
	and where loaders call into it past its start; `.tap`, `.tzx`, `.z80`
	and `.sna` are opened by the file picker. The beeper is a stream of the
	audio service, the time the speaker was high in each of 624 samples a
	frame, and the frames are kept to the sound. Zoom 1 to 3 as Onslaught,
	pause on Escape, the arrows and Tab a Kempston joystick. Closed, it
	keeps where it was: the zoom, the sound, the game, and the machine
	itself, its memory and Z80, all in its config, so it opens again
	paused at that moment.
	`tests/system/test_spectrum.lisp` starts the ROM and loads a game.
*	Stores, `apps/system/stores/`, is what is in stores, two sides as
	Norton Commander had them (#333). A side is the files of this machine,
	its store, or the store of another machine, as folders: an object's
	size, how many are to keep it and how many of the members have it,
	a folder's count and size. What is taken on one side is copied to the
	other, files into a store, out of one, or store to store, and all
	under a folder taken. A folder copied onto one of the same name is
	the two merged: what is in one and not the other is copied, an object
	the same at both is left, and one that is not is skipped, replaced,
	or kept with the new one as name (2), by the rule set. What is in a
	store can be deleted, how many are to keep it set, and pinned, held
	all of by that store's member, or unpinned. A task of its
	own does it, and says how far it has got, and Cancel stops it. A
	file and an object the same byte for byte are left too. Its sides
	and the drawer of Files are each a Sheet, `gui/sheet/`, a scroll
	that keeps its rows its width.

*	A film of MKV or WebM whose Cues say where its keys are, and whose
	frames are each of one length, is read as it is played: opened with its
	head, Tracks and Cues and the first Cluster, how long it is by its
	Duration, and each Cluster read when a frame or a packet of sound in it
	is wanted, found by its time. A seek finds the Cluster of the key before
	the frame by the Cues. Of a film of 1.7 GB in a store on a flash stick
	Films came up in 16 s, every Cluster read first, and does at once. Any
	other is read whole, as before.

*	A film's preview in the file picker reads only as much as shows its
	start: `(reel-open file stream :t)`, of an MKV its first Cluster. A
	preview of a film of 1.7 GB in a store read all of it, and the picker

*	A film's preview is of a frame a tenth of the way in, the first is
	often black, and says how long it is; of an MKV with no Cues, read only
	for its start, its first frame. An MKV with Cues is read as it is
	played for a preview too, as cheap as its start alone.

*	The Pcb app routes by negotiation, PathFinder's way, in place of the
	random search over orders of nets it had. Every net is routed each
	round; a track may short with another net's for a cost, more each
	round and more where they shorted before, till none do. Nets left
	then are routed on the board as it is, and if that does not settle
	them, they and the nets in their way are negotiated again on their
	own, kept only if that leaves fewer. The same board routes the same
	way each time. A routed board's tracks are straightened after: each
	run of a track on a layer pulled tight, from a corner to the farthest
	after it that one segment, or one along an axis and one at 45
	degrees, reaches clear of the other nets; vias and where a net's
	tracks meet stay put, a track is kept only if it is shorter. Every
	route ends with the board checked by drc.inc, as it is printed. The
	app is told when a route ends: its bar is full if
	every net is routed, red where it stopped if not, or if the check found
	a fault, and shows the board
	as it ended. The quant setting is gone, it only grouped nets for the
	old router's search.

*	It routes boards the old router could not: `test4.pcb`, four 0.8 mm
	pitch QFPs and 96 nets between them (grid_res 2), routes complete in

*	The flood is VP, one call for all of it, `flood-wave`: its front and

	nearer another's than both radii and the larger gap, every net's pads
	joined by its own copper, all of it on the board.

*	Pens and fingers are told as they are. A pointer's buttons are only
	buttons, each its own bit: a finger has none, a pen has its tip while

*	A shader can import another file, `(import path)`: its functions,

*	The Whiteboard's min is never smaller than the board's frame can be

## Tools

*	`check` finds a `(bind)` list that ends in `&`, as `(bind '(x y & &)
	(gui-info))`: & there is an error if there is more, which is seldom
	what is meant, and `&ignore` says the rest is not wanted. Where more
	is to be an error, `;check off` on the line. The 33 in the tree are
	`&ignore` now.

*	The test cache names less, so a change runs fewer modules again. What a
	module stands on was every file a string of its, or of anything it
	imports, had the path of, and the command any string started with: a
	check named "key one" stood on the key command and all it imports, and
	tests/suite.inc, under every module, named a test module in its list
	of what is not a module, which imports the net service, and so the
	storage, source and GUI services, login, media and cwb. Every module
	stood on 291 files; 206 of the 1,457 commits since 1 October ran the
	whole suite again for nothing. Now no test module is stood on by
	another, a command is named only on a line that runs one, pipe-run,
	pipe-farm, rack-run or Pipe, and a name is a file, never a folder nor
	anything of .git/. Every module stands on 61 files, and of those
	commits 24 would have run the whole suite, the ones to the suite
	itself. The cache's scan version is 3, every cache is made again.

*	Seventeen test modules are gone, their every check found in another
	module on an input of the same kind, read side by side: test_nums,
	test_mail, test_search, test_storage_scenes, test_storage_scenes_stop
	(the stop scene was run twice in the suite, test_storage_replay runs
	it through the app's runner) and test_document whole; test_integers,
	test_bits, test_system, test_iteration, test_multi_seq, test_sorting,
	test_negative_indexing, test_list, test_scatter_gather, test_strings
	and test_flow once the few checks only they made moved into their

	shifts test_integer_edges asserted twice, are gone too. 182 modules.

*	The release test of the apps on a desktop is one module, test_app_leaks:
	each app opened four times, not five, and looked at the first time as
	test_app_draw looked at it, its window, its words drawn, no plain
	property found as nothing. Benchmark is opened the once, for its
	window. A full `tests -a` on the M4 was 330 s, 254 s of it that one
	module; it is about 200 s now.

*	A char known as the file is written is written as a string, `"\n"`,
	`"\t"`, `"\q"`, `"\\"`, `"\x04"`, not `(ascii-char 10)`: the tree was
	gone over, and a `(cat)` of nothing but strings is one string. `check`
	says so of an `(ascii-char)` of a number or a `+char_` name, and what
	to write. The `+char_` names, lib/consts/chars.inc, are the codes, and
	are had by every task now, root.inc imports them, `+char_nul` added.

*	`(time-add heading body)` adds a body's time to a running total, and
	`(time-report)` prints the totals, how many times and the longest one
	time, beside `(time-it)` in root.inc, for timing what runs too often to
	print each time.

*	What a file imports, includes and makes is read one way,
	`(files-scan path)`, lib/files/files.inc, as the highlighter reads it:
	`make`, `files-depends` and so the GUI's load order and the class
	database's, `includes`, `imports` and the Source service each had
	their own rules of a line, four different. A string is a string now:
	an `(include)` on a line of VP made in a `{}` string, lib/gpu/vp.inc,
	is not taken for one, nor an `(import)` of a path worked out as the
	code runs. `make`'s scans are kept as before; a cold one of the
	system is 39 ms on an M4, the lines alone took 10.

*	`make docs` takes the VP classes from the class database `trace`
	reads, lib/files/info.inc, which keeps a class's file, a function's
	comment and what Lisp calls it with too, and a class's fields from its

	time. A method declared with no kind is a static one, as the
	assembler has it, where the reference listed it as virtual, `:init`
	of `:array`; and a method made in a `(validatecase)` has its comment

	heads only the forms at the top with those first, each at the start

*	`check`'s `scan`: a form `files-scan` looks for that does not begin
	its line, or a `(` that begins a line inside a form of a Lisp file
