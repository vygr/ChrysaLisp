# ChrysaLisp 7.2

The first stage of the GPU and VP compile work. A shader was a picture drawn
over a canvas. It is now also a vertex shader and a pixel shader that draw
triangles, on the nodes or on the GPU, and a typed function that Lisp calls
as native code. With it a file system of our own, a hash and a cipher, and
tests that only run what a change could have broken.

This is a tag, not a GitHub release.

**Update with `make install`.** The host programs and the boot image must
match, the table of calls between them has grown again, shared memory and
the four calls for triangles, and the emulator's divide has changed. An
install from before this cannot build its way forward.

**It is not a compiled Lisp, and is not going to be.** The interpreter and
the small boot image are the core. What is new is a way in to what a machine
has beyond the language, its native floating point, its GPU, for the work
that is all numbers.

## Triangles

*	The shader language has vertex shaders. `defattr` is what is read of a
	vertex, `defvarying` what is handed on to a pixel shader, and a `:mat4`
	can be multiplied. A vertex shader is a file of its own, and goes with
	any pixel shader whose varyings it has, one serves many.

*	Triangles are drawn by the two as native code, with a depth buffer,
	`(shader-vp-draw-tris)`. Each shader is a native function of its own,
	assembled once for the CPU of the node. The Lisp reference,
	`(shader-cpu-tris)`, draws a pixel at a time and the native code matches
	it to the bit.

*	The spaces are those of OpenGL. The eye looks down -z, y is up, the
	front of a triangle is the side its vertices go round counter clockwise
	from.

*	A frame is drawn by all the nodes, a strip each onto a shared pixmap,
	`lib/gpu/tris.inc`. 20,000 triangles over 900 by 900 take 12ms by one
	task on an Apple M4 Max and 5ms by four children, 154ms and 64ms on a
	Raspberry Pi 4. A frame drawn in strips is the frame drawn whole, to the
	bit.

*	The alpha a pixel shader gives is how much of the pixel there is. None
	is skipped, all of it is written, and between goes over what is there.
	A triangle the near plane goes through is cut by it.

*	Native code gives the other tasks of its node a turn as it works, on a
	budget of work done, so a long frame does not stop the node.

*	The Mesh demo draws with all of it, and has CPU and GPU buttons. The flat
	triangle fill it used, `:canvas :ftri`, and `(mat4x4-inv)`, have gone
	from the boot image, nothing else called them. The Molecule app places
	its atoms with a vertex shader and draws them with a pixel shader.

## Triangles on the GPU

*	The same two shader files are drawn by the GPU of the GUI, through Metal
	on a Mac, `(shader-msl-pair)`, and through Vulkan on a Raspberry Pi,
	`(shader-spirv-pair)`, the SPIR-V made word by word in Lisp. The modules
	pass `spirv-val`.

*	The host has four calls for it. A pair of shaders, a mesh, which stays
	on the GPU, and a frame, a pair and a mesh and two blocks for each thing
	drawn. `(shader-gui-pair)`, `(shader-gui-mesh)`, `(shader-gui-frame)`.

*	Edges are smooth, a frame is drawn with 4 samples a pixel where the
	device has that.

*	On a Raspberry Pi 4 the Mesh demo is drawn by its own GPU in 36ms a
	frame, a frame for every tick of the demo's timer, where three of its
	cores take 62 to 98ms.

*	Two apps on the GPU share it. A draw waits for another canvas's draw
	only if that one is more than a moment old, which on a fast GPU none is,
	and what is refused has the next turn. With the Surface and Mesh demos
	together, Mesh draws every frame on an M4, where it drew 216 of 299. On
	a Pi it draws 465 frames in 35 seconds, where it drew 61, and the
	display is still drawn 36 times a second.

## Functions for Lisp to call

*	A file with no `main` is functions, not a shader. `(shader-vp-func
	program name)` makes one a native function that Lisp calls as any other,
	`(place matrix point)`. Numbers, vectors and matrices in, one of those
	out, new.

*	It is as quick as VP written by hand. A matrix by a matrix, typed
	against `(mat4x4-mul)`, 52ns and 51ns on an Apple M4 Max, 112ns and
	114ns on a 2018 x86_64 MacBook Pro, 518ns and 518ns on a Raspberry Pi 4,
	the answers the same to the bit.

*	The native code of a vertex shader reads and writes a vertex where it
	is. 65,536 vertices placed by a matrix take 116us on the M4, where the
	library's routine, by hand, takes 131us.

*	`shader -t vp file` shows the VP of any of them, a pixel shader, a vertex
	shader, or each function of a file.

## Native code is a cache

*	A shader file is known by a SHA-256 of it. `(shader-load file)` takes the
	hash and reads only the head of the file. The native function is looked
	for under that hash and bound, with no body read, checked or made again.
	Loading the raymarch shader when its code is there went from 4.2ms to
	0.14ms on an M4, and from 41ms to 1.0ms on a Pi, and every task that
	uses a shader does it.

*	A back end is known by a hash of the files it is written in. A change to
	one can not find what the old one made, and there is no number to
	remember to change.

*	The Metal text and the SPIR-V of a file are kept the same way.

*	It all works with the cache cleared, slower the once.

*	The assembler refuses a function over 64KB. It wrote one with a length
	that had wrapped.

## Tests

*	The tests are a cache of results. A module is run again only when
	something it stands on has changed, what it imports, a file or a command
	it names, the boot image or a host program. A change to a library runs
	its own tests, a change to the boot image runs them all, a change to a
	doc runs none. `tests -a` runs every one whatever the cache has, which
	is what a release is tested with. `docs/ai_digest/test_cache.md`.

*	New `lint` command. A debug build, the trace lint of every listing, and
	the release build back, in the one go.

*	A command from a script took 2 seconds longer to end than it needed, a
	pipe waited for a stream that had already stopped. `make all boot` from
	a shell is 0.67 seconds and was 2.7. All the tests are 5 seconds on an
	M4 and were 9. With nothing to run again, 0.58 seconds.

*	An error thrown by the function given to `(pipe-run)` is an error. It
	was a task that waited for ever, the pipe was let go of still open.

*	4,289 tests in 89 modules. They pass in any order, run one after
	another in the one task.

*	Every test passes on RISC-V and on LoongArch under QEMU, and a self
	hosted build on each gives the boot image the Mac cross builds, to the
	byte.

## The same on every CPU

*	A divide means the one thing on ARM64, x86_64, RISC-V, LoongArch and the
	emulator. It is of a number of 64 bits. By 0, with no check in front of
	it, the answer is 0 and what is left over is the number. The most
	negative number by -1 is itself. x86_64 stopped the node for the last
	two, and RISC-V gave another answer for the first. The usual build still
	makes an error of a divide by 0, its check is there.

*	Reading a number with a point that is too big for a fixed stopped an
	x86_64 node. It is a number now, a wrong one, and the node carries on.

## A file system, a hash and a cipher

*	exFAT, `lib/fs/exfat.inc`, read, written and formatted, on a file of the
	host, a memory stream, or a raw device. A 4GB flash stick formatted by
	ChrysaLisp passes macOS's checker and mounts, and the two have taken
	turns writing to a volume. It is for the day there is no host to ask.

*	FAT32 is read, `lib/fs/fat32.inc`. The boot partition of a Raspberry Pi
	comes back to the byte.

*	New `lib/crypto/`. SHA-256 and HMAC. ChaCha20 with Poly1305, RFC 8439,
	`(aead-seal)` and `(aead-open)`, data hidden and guarded. Random bytes
	from the host, and a key from a password, `(pbkdf2-sha256)`. The work on
	each block is VP. On one core of an M4,
	SHA-256 253MB a second, ChaCha20 441MB, a seal 378MB, with none of the
	instructions a CPU may have for it. `docs/ai_digest/crypto.md`.

*	The Windows host program made its random bytes with `rand()`. It asks
	the system now.

*	Notes on a storage service, an idea, not built,
	`docs/ai_digest/storage_service.md`.

## Nodes working together

*	The queue and farm every app had a copy of is one library,
	`lib/task/jobs.inc`. The assembler, the command farm, and every app that
	farms work out but Chess, are on it, and a full build is no slower.

*	A pixmap can have its pixels in shared memory, for the nodes of one
	machine to draw on together. The Canvas, Opcodes and Bubbles demos are
	each a scene drawn by all the nodes, a slice each, and the picture is
	the one a single task draws, bit for bit.

*	A build on one node is a fifth quicker, and a build whose workers can
	not answer stops and says so.

*	The end of a terminal's input reaches the command it is running, and a
	pipe no longer loses the last of what a command said.

## Films

*	A film is written as a stream, frames pumped in and the `.flm` out,
	`lib/streams/flm.inc`. The Raymarch demo draws its film on the GPU and
	records straight into one. On a Raspberry Pi 4 it took 79 seconds to
	draw, save and make, and takes 44.

*	An opaque color is premultiplied to itself. It lost a level, and a film
	went a touch darker as it began to play.

## The boot image

*	238,532 bytes on ARM64. `lib/crypto/` is 5,944 of them, all native code
	outside `apps/` is in it.

## Not ready

*	GPU triangles have not been run on Windows. The host programs are built
	for it. The snapshot has those of 7.1 till it is made again.

*	The GLSL back end has no vertex stage.

*	Compute on a GPU. The Metal and SPIR-V back ends refuse a file of
	functions.

*	A function that is bound stays bound. There is no way yet to make one
	that is already loaded go stale.

*	An object is taken to be solid. A see through one drawn with no cull
	does not show its own back faces through its front.

*	The native code of the hash and the cipher loads 4 and 8 bytes from
	wherever in a str it is told to start. That has run on RISC-V and
	LoongArch under QEMU, and not on a real one of either.

*	The `fmt` command is still parked. Do not use it on the tree.
